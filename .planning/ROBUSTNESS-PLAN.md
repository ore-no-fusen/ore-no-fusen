# 俺の付箋 安定化マスタープラン（縮小版）

**作成日:** 2026-07-13
**方針:** 100万人規模を想定し、データ損失につながる対策は実施する。一方、運用負荷と新しいバグを増やす大規模基盤は作らない。

## 1. 実施判断

### 必須として実施する7項目

1. `settings.json` の原子的保存と破損時復旧
2. 保存先フォルダの異常検知
3. 未保存データの最小退避
4. 複数窓・外部変更との保存競合防止
5. バックアップの復元可能性検証
6. PC–iPhone同期の冪等化
7. 障害系回帰テストと実機試験

### 縮小して実施する3項目

1. 削除・移動・リネームは全面共通化せず、既存経路を個別監査して不足する安全策だけ追加する。
2. クラッシュ復旧は複雑な復旧センターを作らず、自動復旧または隔離コピー保存に限定する。
3. 診断は独自基盤を作らず、既存Sentryと最小ローカルログへ必要情報だけ追加する。

## 2. 非目標

- 新しいノート機能や同期先の追加
- エディタや画面全体の作り直し
- 保存形式の全面変更やデータベース化
- 複雑な復旧画面、ログ管理画面、監視サーバーの新設
- 正常時の確認ダイアログや設定項目を増やすこと
- 安定化と無関係なリファクタリング

## 3. 実施計画

### 第1段階: PCローカルデータ保護

**概算:** 3〜5週間

#### 1-1 設定ファイルの安全化

- `settings.json` を一時ファイルへ書き、JSONとして再読込できることを確認してから置換する。
- 直前の正常世代を1世代だけ保持する。
- 現行設定が壊れている場合だけ、検証済み直前世代を使用する。
- 正常設定と復旧用設定を混同しない。
- 本体と直前世代が両方壊れた場合だけ、両方を日時付きで退避し、安全な既定保存先を持つ正常設定を再作成する。
- 自動復旧後は黄色い案内付箋1枚で異常とデータ非削除を伝え、専用レスキュー画面を増やさず通常利用を継続する。

**合格条件:** 書き込み中断、空ファイル、不正JSONを模擬しても、正常世代または直前世代で起動できる。

#### 1-2 保存先異常の検知

- 起動時と書き込み失敗時に、保存先の存在、ディレクトリ種別、書き込み可能性を確認する。
- 容量不足、権限不足、外付けドライブ切断を区別して通知する。
- 異常時は新規作成、自動保存、削除、設定上書きを止める。
- 通常画面へ進めない重大異常だけ、既存の設定・保存先異常導線を利用する。

**合格条件:** 保存不能状態で、既存ファイルを空内容や古い状態で上書きしない。

#### 1-3 未保存データの最小退避

- 編集中本文をアプリ管理領域へ原子的に退避する。
- 退避情報は付箋パス、内容識別子、更新時刻に限定する。
- 正常保存後は対応する退避だけ削除する。
- 強制終了後、保存済み本文より新しい退避だけを自動復旧候補とする。
- 自動判定できない場合は本文を上書きせず、隔離コピーとして残す。

**合格条件:** 入力直後と保存中の強制終了から最新編集を回収でき、正常終了後には不要な退避が残らない。

#### 1-4 保存競合の防止

- 読み込み時の内容識別子を保存し、保存直前にディスク上の現在値と照合する。
- 不一致なら無言上書きを拒否し、両方の内容を保持する。
- 同じ付箋の複数窓、外部エディタ変更、アラーム更新、フロントマター更新を対象とする。
- 重複ウィンドウ生成防止を再監査するが、ウィンドウ管理全体は作り直さない。

**合格条件:** 古い画面や外部処理が、新しい本文を上書きしない。

### 第2段階: 復旧保証とファイル操作監査

**概算:** 1〜2週間

#### 2-1 バックアップ復元保証

- バックアップ生成後に対象件数、サイズ、読み取り可能性を検証する。
- 隔離された一時復元先へ展開し、Markdownと必要画像を読み取れることを確認する。
- 新バックアップの検証完了前に、既存の正常バックアップを入れ替えない。
- 復元試験は現行保存先とバックアップ原本を変更しない。

**合格条件:** 「検証済み」と表示されたバックアップは隔離先で読み出せる。

#### 2-2 削除・移動・リネームの安全監査

- 通常付箋、タグ移動、アーカイブ、ゴミ箱、クリスタルを経路ごとに監査する。
- 移動成功前に元を消さない、多重実行を防ぐ、失敗時に元を保持する、の3条件を確認する。
- 不足する経路だけ最小修正する。
- 共通トランザクション基盤への全面移行は行わない。

**合格条件:** 各操作を途中で失敗させても、元または検証済み移動先の少なくとも一方が残る。

### 第3段階: PC–iPhone同期の安全化

**概算:** 2〜3週間

- 送信単位に安定したメッセージIDを付け、PC、Service Worker、IndexedDBで共通利用する。
- 受信処理を取得、検証、ローカル確定、受信済み記録、Drive削除に分ける。
- 同じメッセージの再配送で付箋や画像を重複生成しない。
- 本文成功・画像失敗などの部分成功を記録し、再試行では不足分だけ補う。
- Drive削除失敗を受信失敗と混同せず、次回安全に清掃する。
- オフライン、トークン更新、push重複、Service Worker再起動、PC再起動を試験する。

**合格条件:** 各段階で停止・再開しても一件の結果に収束し、欠落があれば明示される。

### 第4段階: 品質ゲートと最小診断

**概算:** 1〜2週間

#### 4-1 障害系回帰テスト

- 保存中断、設定破損、二重保存、移動失敗、バックアップ破損を自動テストへ固定する。
- PC–iPhone同期はDriveモック統合試験と実機試験を分離する。
- Windows/Tauri、iPhone、Service Workerでしか確認できない項目は、再現手順、期待結果、証跡形式を固定する。
- リリースごとの必須ゲートと、時間のかかる実機ゲートを分ける。

#### 4-2 最小診断

- 保存、移動、バックアップ、同期、復旧に匿名の操作IDと結果を残す。
- 記録項目は操作種別、成功・失敗、エラー分類、復旧有無に限定する。
- 本文、アクセストークン、不要なフルパスは記録しない。
- 既存Sentryとローカルログを利用し、新しい監視サービスや管理画面は作らない。
- ユーザー向け表示を「何が失敗したか」「データは安全か」「次に何をするか」に統一する。

**合格条件:** 7つの必須リスクすべてに自動試験または必須実機試験が対応し、障害時のデータ安全性を判断できる。

## 4. 実施順序

```text
第1段階 PCローカルデータ保護
  → 第2段階 復旧保証・ファイル操作監査
    → 第3段階 PC–iPhone同期安全化
      → 第4段階 品質ゲート・最小診断
```

ローカル保存と競合防止を安定させてから、Drive・Service Worker同期を変更する。

## 5. 共通の進め方

1. 対応する `docs-v2/` のシーケンス番号と現行動作を確認する。
2. 不具合の場所、根本原因、影響範囲、最小修正を説明してユーザー確認を取る。
3. 失敗を再現するテストを先に追加する。
4. 一度に一つの保存・操作経路だけ変更する。
5. ユニットテスト、Rustテスト、TypeScript、lintを実行する。
6. 対象経路のE2Eまたは実機試験を行う。
7. `docs-v2/` と `CURRENT.md` を更新する。
8. 段階ごとに停止し、次へ進む前にユーザー確認を取る。

## 6. リリースと切り戻し

- 各段階を独立して検証・リリース・切り戻し可能にする。
- 旧データ形式を読める状態を維持し、不可逆な一括移行を行わない。
- 第3段階の同期変更は、PCローカル保存の安定化と別リリースにする。
- 正常に動いている経路を、設計上の統一だけを目的に作り直さない。

## 7. 見積もり

| 区分 | 目安 |
|---|---:|
| 第1段階 | 3〜5週間 |
| 第2段階 | 1〜2週間 |
| 第3段階 | 2〜3週間 |
| 第4段階 | 1〜2週間 |
| 全体 | 7〜12週間 |

最大の不確実要素は、Drive、Service Worker、IndexedDB、iPhone実機をまたぐ同期障害試験である。

## 8. 次の作業

最初に第1段階のうち「設定ファイルの安全化」を詳細調査する。設計書の該当シーケンスと現行コードを確認し、修正前説明と詳細実装計画を提示する。ユーザー確認後にのみ実装へ進む。
