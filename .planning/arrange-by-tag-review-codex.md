## 高優先の指摘

1. **座標系の仕様が不足（最重要）**
   - 既存 `app/api/window.ts:31` は物理座標を scaleFactor で割って frontmatter 用の論理座標にしている。
   - 一方 `src-tauri/src/lib.rs:1396` の `fusen_show_at_position` は**物理座標**を受ける。
   - 計画書に「計算・保存・set_position の座標系」を明記すべき。
   - **推奨**: frontmatter/AppState は論理座標。OS 移動時だけ物理座標へ変換。monitor/workArea も同じ座標系に正規化。

2. **マルチモニターの「元あった場所に近い方」が曖昧**
   - 各付箋を現在モニターごとに分けてそのモニター内でタグ整列するのか、タグ単位で代表モニターへ集約するのか未定。
   - 前者＝同じタグが複数モニターに分裂、後者＝一部付箋が大きく移動。
   - **目的が「飛ばさない」なら `monitor → tag → color` の順でグルーピング**が妥当。

3. **横方向のあふれが未定義**
   - 計画は色列の縦あふれだけ。タグ数や色列幅が多いと右端を超える。
   - workArea 幅を超えたタグブロックは次段へ折り返す、または開始位置を現在の付箋群の重心近くから決める、のどちらかが必要。

4. **付箋が画面より大きい場合の扱い**
   - 「サイズは変えない」はよいが、`width > workArea.width` / `height > workArea.height` の付箋をどうするか明文化が必要（左上だけ入れる／はみ出し許容／最小表示領域だけ保証）。

5. **整列の取り消し（undo）を入れるべき**
   - ボタン1発で自由配置を上書きするので、最低でも1回分の「直前配置へ戻す」が必要。
   - AppState に直前の `{path, window}` スナップショットを持つ。永続化は MVP 外でも可。

## レイアウト案

- 現行「タグ内を色列」は色の意味が強いなら妥当。横幅を食いやすいので **MVP は空色列を詰める** でよい。
- 代替案: タグブロック内を色順ソートの**タイル詰め**にすると横の爆発を抑えられるが、色を列として把握する力は落ちる。→ 今回は現行案を採用し、横あふれだけ補うのがよい。

## 7-1（固定5色以外の自由色）の推奨

- **案A: 各タグ右端に「その他」列** を推奨。
  - 案B（近似色分類）はユーザー意図と違う分類になりやすい。
  - 案C（対象外）は「ボタン1発で全体を俯瞰」と矛盾。
- その他列の中は色コード昇順、同色内は既存順／更新順で安定化。

## 実装上の落とし穴

- **色定義の重複**: 現状 `useStickyNoteContextMenu.ts:262` に直書き。Rust 側にも同じ順序を持つと重複定義。最低限、テストで `#f7e9b0/#ffcdd2/#80d8ff/#fafaf0/#cfd8dc` の順序を固定する。
- **frontmatter window のフォーマット維持**: `logic.rs:134` の正規表現は順序固定。更新時は `window: { x, y, width, height }` の形式を必ず維持。
- **反映順序と途中失敗**: 「新配置を計算 → ウィンドウ移動結果を集める → 成功分だけ AppState/frontmatter 更新」が安全。途中失敗時の扱いを決める。
- **`updated` を変えない**: 整列は内容変更ではないので、位置だけ更新し `updated` を触らない（履歴・同期の意味を濁さない）。
- **一括移動のパフォーマンス／ちらつき**: 逐次 `await set_position` は遅い。全ウィンドウを foreground にするとちらつく。Rust 側で**フォーカスを奪わない一括移動コマンド**にする。
- **`fusen_show_at_position` の流用注意**: これは表示/フォーカス用途で副作用が強い。整列にそのまま使わず、位置変更のみ・フォーカス変更なしの専用経路を用意する。
