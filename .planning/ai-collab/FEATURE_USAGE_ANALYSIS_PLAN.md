# 匿名の機能利用分析・おすすめ検討の準備案

作成: 2026-09-04
状態: 準備完了・アプリ実装前レビュー用。実測結果ではない。

## 目的と完成条件

1. Aさん・Bさん相当の匿名アプリ個体ごとに、対象期間の利用日数、使った機能、利用が観測されない機能を確認する。
2. 全体について機能別の利用者数・利用率・継続利用を確認する。
3. 利用履歴とおすすめルールを照合し、理由付きの改善提案候補を作る。実際の配信は今回の対象外。

Aさんは人の本人確認ではなく、同意済みアプリ個体の仮名。同一PCの複数付箋と再起動を同一個体として扱う。別PC・再インストールは別個体になり得る。氏名・メール・PC名・Driveアカウントを取得して結び付けない。

## 現状の証拠と不足

- GA4の機能利用イベントは受信しているが、7機能のみ。本文の階層折りたたみ・既存付箋の編集などは含まれない。
- AnalyticsLoader.tsxは各WebViewでgtagを初期化。アプリ自身による共通識別子の管理は未実装。GA既存識別子の共有・再起動継続性は実機で未検証であり、現在のGA人数をそのまま人数と断定しない。
- app_version/distributionはapp_startedのみ。distributionはdesktop_app固定。開発版と一般配布版が混在し得る。
- usage_snapshotは起動時のみ。常駐中に使い続ける状況を捉えない。
- useNoteFile.tsのsaveNoteContentは保護のため保存せず正常returnする経路がある。一方StickyNote.tsxはawait完了だけでfirst_note_saved/alarm_setを送る。実保存成功とスキップを区別する必要がある。
- AnalyticsConsentDialog.tsxの送信項目説明に既存の機能利用・枚数範囲が含まれず、docs-v2/100_PRIVACY.mdとの不一致がある。
- GA4の新規カスタムディメンション7件は登録済み。ただし9/3までの枚数内訳は全126イベント/8ユーザーがnot set。過去の機能別履歴・未使用を再構築できるとは約束しない。

## 分析単位とデータ設計

- まず既存GA識別子が主画面/付箋/再起動で一致するか実機確認する。一致しない場合、同意後に生成するランダムなアプリ個体識別子をRust AppState側で保持し、全ウィンドウのGAクライアント識別を統一する。GA実装方法は公式仕様・実機で確定してから変更。
- 識別子を高カーディナリティのカスタムディメンションには登録しない。ユーザーエクスプローラ、必要時はBigQueryのuser_pseudo_idで扱う。
- 主状態・同意・同一操作の重複防止・日次記録はRustに集約。frontendは成功したユーザー操作を通知する。復元、再描画、自動初期化を利用操作として数えない。
- 全計測にapp_version、環境区分(production/development/test)、計測仕様版を付ける。開発・テストは本番GAへ送らない。
- feature_used: feature_nameと必要な固定actionのみ。本文・ファイル名・タグ名・検索語・正確な保有枚数は送らない。
- app_active_day: ユーザーによる対象操作があった日だけ1回。自動起動とバックグラウンド処理だけでは送らない。時刻境界を固定し複数窓・再起動でも重複しない。
- usage_snapshot: 起動直後の初期化完了後および当日最初の実利用時に、固定範囲の保有状況を取得。取得失敗を0枚へ変換しない。最新値の時刻と取得可否を保持する。
- 通信失敗時の再送キューなし、操作を待たせないという現行仕様を維持。したがってイベントなしは未使用の証明にはならない。
- 過去に使ったことがあるという累積値と、期間内の操作を区別する。導入以前の履歴は不明。

## 追加改訂: 会員番号との統合案（2026-09-04）

ユーザー追加要望により、前述の「掲示板と自動連結しない」は次の設計で具体化する。利用者に連結目的を説明し、同意を得た場合だけ分析用識別子と会員番号をサーバー側で対応付ける。問い合わせ利用は計測同意を必須にしない。

### 実施内容

- 会員区分別の通番をサーバーで自動発行する（一般会員: 10000、10001…／有料会員: 1、2…）。サーバーの原子的な採番処理と一意制約で重複を防ぐ。オフライン中はローカル識別子を保持して登録待ちとし、確定番号と区別する。
- Rust AppStateを唯一の状態として番号と認証情報を管理。秘密情報はWindowsの保護ストレージを使う設計を優先し、通常設定・GA・Discord・ログへ秘密を出さない。
- 設定画面に会員番号とコピー操作を追加。問い合わせ、開発者側のDiscord通知、返信の管理で会員番号を表示する。返信の宛先はサーバー検証済みの既存conversation_idで決める。
- 既存のlocalStorageのconversation_id/secret_tokenを所有確認の上で一度移行する。既存の会話と返信を保持し、会員番号の再発行を防ぐ。
- 会員番号と分析IDは分離。管理者だけが対応表を読めるようにし、GAに会員番号・問い合わせ本文・秘密トークンを送らない。
- 会員ごとの利用表、全体機能利用率、理由付きおすすめ候補を作る。対象期間と観測不足を必ず表示。配信は初期工程では行わない。
- 会員別分析と問い合わせ連結を同意画面へ明記。同意撤回後は計測と新たな紐付けを停止。過去データ削除はGA/対応表/分析エクスポートにまたがる手順を用意。問い合わせ履歴削除とは区別する。

### リスクと対応

1. 連結により単なる集計より追跡性が高くなる。匿名と断言せず仮名化したインストール単位データとして説明し、新しい目的への同意を確認する。
2. 公開番号を認証に使うと会話を乗っ取られる。番号と秘密トークンを分離し、既存会話への全投稿は所有確認後に処理する。
3. 既存投稿APIはprovided conversationIdを受け、所有確認前にlistLatestMessagesを呼び、その後createConversationへprovided tokenのhashを渡す経路がある。悪用成立範囲は未試験だが、会員拡張前の優先修正項目。読み取り側のトークン検証だけでは十分でない。
4. 設定消失/再インストール/設定コピーにより会員分裂・共有が起き得る。番号入力だけで復元させず、復元は本人保持の秘密による別工程。初版は単一インストール単位を明示する。
5. 旧会話の移行失敗で返信が消える。旧認証をサーバーで検証してから原子的に対応付け、完了前に旧情報を消さない。
6. 通信欠損・未同意・旧版を未使用と判定する危険。未観測/未対応/不明を区別し、判定可能な母数だけで利用率を出す。
7. 管理用対応表の漏えい・Firestore/BigQuery費用・外部保存期間の不一致。管理者認証、クライアント直接アクセス禁止、保持期限、削除ジョブ、予算上限を設計。新規クラウド接続・課金は今回未実施。
8. おすすめが不要な人への過剰案内。まず候補を人が確認し、将来の表示は非表示・頻度制限を付ける。

実施順: 仕様と同意 → 投稿API認証修正 → 会員発行/旧会話移行 → 計測の正確性/機能追加 → 実データ分析 → おすすめ候補の評価。


### 会員番号の通番化（ユーザー指定・2026-09-04）

- 表示用会員番号はランダムではなく1からの昇順通番（ゼロ埋めなし）。分析用識別子と認証用秘密トークンは推測不能な別値のまま維持する。
- サーバー側で登録要求の冪等性を保証し、同一インストールの再試行で番号を増やさない。カウンター更新と会員作成をトランザクションで実施。開発・テスト環境の採番を本番から分離する。
- 初回サーバー登録日時を保存し、会員一覧に表示する。登録順の目安は番号、正確な登録時期は日時で確認する。
- 既存ユーザーは新方式へ登録した順であり、過去の実際の利用開始順ではない。過去の開始時期は不明とし、登録日時を利用開始日時と偽って扱わない。オフライン初回起動と登録日時にも差が出る。
