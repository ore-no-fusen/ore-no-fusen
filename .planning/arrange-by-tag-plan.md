# 計画書：付箋の整列（タグのかたまりの中を色で並べる）

作成日: 2026-06-17
最終更新: 2026-06-17
対象バージョン: v4.0.2 ベース
ブランチ: develop
状態: **設計確定（未決定なし。実装に進める）**

---

## 1 目的

散らばった付箋を、ボタン1発で **タグごとのかたまり**に整列させる。
さらにそのタグのかたまりの中を **色（黄→赤→青→白→黒）** で小分けして並べる。
「どのタグに何がどれだけあるか」を瞬時に把握できるようにする。

MVP「大事なことは貼っておけばいい」の延長線上にある機能。
貼った付箋が増えても、タグと色のかたまりで俯瞰できれば「そこに残る」価値が保たれる。

---

## 2 前提タスク：白・黒の付箋色を先に追加する（整列より先）

整列は「色の固定順」で列を分けるため、**白・黒が付箋色として存在しないと固定順に組み込めない**。
後から色を足すと整列のロジックも触り直す二度手間になるので、**白・黒の追加を先に実施する**。

- 追加先: `app/hooks/useStickyNoteContextMenu.ts` の色サブメニュー（現在 青/赤/黄の3色）
- 「一度に一つ変える」の原則に従い、**整列とは別タスク・別コミット**で行う
- 追加する色: 白 `#fafaf0`（クリーム寄り）／黒 `#cfd8dc`（青み淡グレー＝パステル調）
- 本文は黒字のまま。実物プレビューで黒字の読みやすさを確認のうえ確定した
- **メニューの並び順を整列順に統一（確定）**: 現状メニューは「🔵青→🌸赤→💛黄」で、整列順（黄→赤→青）と逆。
  この機会に **💛黄→🌸赤→🔵青→⬜白→⬛黒** に並べ替える。
  - 理由: 色を選ぶメニューと整列の色順がバラバラだと、ユーザーも開発者も混乱する。順番を1つに揃える。
- メニュー文言（i18n）: 白・黒のラベルを `lib/i18n.ts` に追加（ja/en 両方）。

**ブランチ運用（確定）**: この前提タスクは規模が小さいので **`develop` で直接**作業する。
（リリース手順書 `docs/010_RELEASE.md` の「アプリに影響する小さい変更」に該当）。
整列が白黒5色を前提にするため、**この前提タスクを先に develop に入れてから**整列本体に着手する。

## 3 並べ方（確定した仕様）

### 3.1 基本レイアウト（タグの中を色で分ける入れ子構造）

第1のまとまりは**タグ**。タグのかたまりの中を、さらに**色（黄→赤→青→白→黒）**で小分けして横に並べる。
これを全タグ分くり返す。

- **大ブロック = タグ**（仕事のかたまり、家庭のかたまり…）を左から順に並べる
- 各タグの中で **色ごとに列**を作る：黄→赤→青→白→黒の固定順で左から
- **行（縦方向）= 同じタグ・同じ色の付箋**：上から積む
- **付箋のサイズは変えない**（今のまま並べる。fold もリサイズもしない）

```
        タグ「仕事」                        タグ「家庭」
  ┌──────────────────────────┐    ┌──────────────────────────┐
   黄    赤    青    白    黒        黄    赤    青    白    黒
  ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐    ┌──┐      ┌──┐      ┌──┐
  │仕│ │仕│ │仕│ │仕│ │仕│    │家│      │家│      │家│
  ├──┤ └──┘ └──┘ └──┘ └──┘    └──┘      └──┘      └──┘
  │仕│                            （その色が無い列は空＝詰めない）
  └──┘
   ↑タグの中を色で分ける              ↑次のタグを右隣にくり返す
```

### 3.2 並べる手順（全タグを回す）

1. 全付箋から **タグ一覧**を作る
2. タグごとにループ（タグ順は 4.2）:
   - そのタグを持つ付箋を集める
   - 黄→赤→青→白→黒 の固定順で、色ごとに列を作る（色は固定順 3.3）
3. 次のタグへ進み、その右隣に同じことをくり返す

> ある色の付箋が0枚のとき、その列を **詰める（左に寄せる）か、空けて固定位置を保つか** は実装時に決める。
> 初期実装は「空けない（詰める）」とし、列幅を無駄にしない。

### 3.2.1 縦の積み順（同じタグ・同じ色の中・確定 26-06-20）

同じタグ・同じ色の付箋を縦に積むとき、**作成日（seq）順で新しいものが上**。

- 順序キー: ファイル名 `{seq}_{date}_{context}.md` の **seq（連番＝作った順）**。seq が大きいほど新しい。
- 並び: **seq 降順（新しい＝上、古い＝下）**。
- 採用理由: 更新日 `updated` は整列で変えない設計（5.3）で並びが揺れにくいが、ユーザーは「作った順・新しいのが上」を選択。seq は作成順で固定なので安定（再整列しても同じ並び）。
- **実装方針（arrange.rs は変えない）**: arrange.rs は入力 `notes` の順序を保って各色列に積む（並べ替えしない）。
  よって **lib.rs 側（部品②のメタ取得）で notes を seq 降順にソートしてから** `calculate_arrange_by_tag_positions` に渡せば、各列が新しい順に積まれる。二重ソートなし。
  - seq は `ArrangeNote` に無いので、ソート用に各付箋の seq を別途取得する（ファイル名 or frontmatter の seq）。
    既存の `parse_filename`（logic.rs）が `(seq, created, context)` を返すので流用できる。
- **変更容易性（確定 26-06-20・方針A）**: 並び順は後で変える可能性がある。今は「seq 降順（新しいのが上）」固定だが、
  **並び順を決めるソート処理を lib.rs の1か所に集約**しておく（比較関数 or ソートキー1か所）。
  将来「更新日順」「古いのが上」等に変えたくなったら、そこを1行直すだけで切り替えられるようにする。
  実行時に切り替えるUI（設定画面）は今は作らない。必要になったらこの1か所を土台に設定画面（方針B）へ発展させる。

### 3.3 色の固定順

実装の色定義（`app/hooks/useStickyNoteContextMenu.ts` のコンテキストメニュー）に合わせる。

| 順 | 表示名 | 色コード | 備考 |
|----|-------|---------|------|
| 1 | 黄 | `#f7e9b0` | デフォルト付箋色 |
| 2 | 赤（ピンク） | `#ffcdd2` | メニュー上は「ピンク 🌸」 |
| 3 | 青 | `#80d8ff` | |
| 4 | 白 | `#fafaf0` | クリーム寄りの白。**前提タスクで追加**（第0章） |
| 5 | 黒 | `#cfd8dc` | 青み淡グレー（パステル調の「黒」）。**前提タスクで追加**（第2章） |

- 黄→赤→青→白→黒 の順で列を作る。
- **5色以外の付箋（確定）**: 黒のさらに右に「その他」列を作ってまとめる。
  - 補足: アプリ上は色変更がこの5色の固定選択のみで（`useStickyNoteContextMenu.ts`、自由入力なし）、
    通常は5色以外の付箋は発生しない。frontmatter を手で書き換えた等で5色外の値が来た場合の受け皿。
  - その他列の中の並びは色コード順で安定化する（実装時）。

### 3.4 あふれた時（トランプ風の重ね）

1つの色の付箋が多くて画面の下端を超えたら、超えた分を **少しずつ下にずらして重ねる**（トランプのカードのように）。

- 同じ色は必ず1列を保つ（次の列に折り返さない）
- 重ね send の量（例: 40px ずつ）は実装時に調整

```
│ ┌──────┐ │  下端まではフルの高さで積む
│ │ 黄 A │ │
│ │┌─────┴┐│  下端を超えたら
│ ││黄 B  ││  少しずつずらして重ねる
│ │└┌─────┴┐
│ │ │黄 C  │  ← トランプ風
│ └─└──────┘
```

### 3.5 起動方法（UI）

整列はアプリ全体に関わる操作なので、特定の付箋ウィンドウのボタンではなく、
**タスクトレイのメニュー**から起動する。

- 追加先: `src-tauri/src/tray.rs` の既存メニュー（新規メモ／検索／全部隠す…が並ぶ場所）
- メニュー項目（例）: 「タグで整列する (Arrange by Tag)」を追加
- 押した瞬間に全付箋が並ぶ。元の自由配置は上書きされる（整列 ON/OFF トグルではない）
- 直後に **「整列前に戻す (Undo Arrange)」** を出せるようにする（取り消し・7.x 参照）
- 既存実装に倣う: `MenuItem::with_id` で項目追加 → `on_menu_event` の `match` に分岐追加。
  新しい仕組みは不要（トレイメニューは既にある）。
- ショートカット併設は任意（既存の `Ctrl+Shift+H` 等と衝突しないキーにする）

### 3.6 配置パラメータ（実装時の初期値・調整可）

| 項目 | 初期値 | 説明 |
|------|-------|------|
| 開始位置 | `x=40, y=40` | 画面左上の余白 |
| 色の列の横送り | その列で一番広い付箋の幅 + 20px | 列が重ならない幅 |
| タグ間の追加の余白 | 40px | タグのかたまりの境目を分かりやすくする |
| 行の縦送り（下端まで） | 各付箋の高さ + 20px | フルで積む |
| 行の縦送り（あふれ後） | 40px ずつ | トランプ風の重ね |

## 4 複数タグ・並び順・出力先（確定）

### 4.1 複数タグ
- 複数タグが付いた付箋は、**最初のタグ（`tags[0]`）のかたまりにだけ置く**。
- 付箋＝1ウィンドウなので、同じ付箋を複数のタグに重複表示することはできない（物理的に不可）。
- そのため、2個目以降のタグのかたまりには、その付箋は現れない。

### 4.2 タグのかたまりを左から並べる順
- **付箋が多いタグ順**（左ほど多い）。関心ごとの大きさ順に並ぶ。
- 付箋を足すと並びが変わりうるが、「関心ごとの量で俯瞰する」目的に合う。
- 同数のタグが並んだときの順序（タイブレーク）は実装時に決める（例: タグ名順で安定化）。
- **枚数の数え方（確定）**: 「そのかたまりに**実際に置かれる**付箋数」で数える
  ＝各付箋を `tags[0]` のタグにだけ計上する。
  - 理由: 4.1 で付箋は `tags[0]` のかたまりにしか置かれない。もし全タグで二重に数えると、
    順位を決める枚数と、実際に並ぶ列の長さがズレて、スカスカの列が左に来るなど不自然になる。
  - 注意: 既存の `get_all_unique_tags`（`logic.rs`）は全タグを集める＋名前順ソート。
    整列のタグ順はこれをそのまま使えないので、**`tags[0]` 基準で集計し直す**必要がある。

### 4.3 タグなしの付箋
- タグが1つも付いていない付箋は、**全タグのかたまりの右端に「タグなし」ブロック**としてまとめる。
- その中も色の固定順（黄→赤→青→白→黒）で並べる。

### 4.4 どの画面（モニター）に出すか（`tag → color`・全付箋を1モニターに集約）

**確定（26-06-20 変更）**: 全付箋を**メインモニター1枚に集めて**整列する。グルーピングは **タグ → 色** のみ（モニターでは分けない）。

- 整列を押すと、どのモニターにあった付箋も**メインモニターの作業領域に集約**され、タグのかたまり（4.2 の順）× 色の固定順（3.3）で並ぶ。
- **タグが複数モニターに分裂しない**＝「タグごとに俯瞰する」目的を最優先。
- 配置の基準は**メインモニターの作業領域（workArea＝タスクバー等を除いた範囲）**。1枚分。
- **モニター判定は不要**: 旧仕様（`monitor → tag → color`・付箋を元モニター内で整列）は破棄。
  各付箋の所属モニター判定（`monitorFromPoint` / Rust `monitor_from_point`）は**使わない**。
  → 未検証の Rust monitor 判定 API が不要になり、実装が単純化（旧・部品⑥は削除。5.8 参照）。
- 集約先の「メインモニター」＝**Windows の主ディスプレイ**（ユーザー確定）。Tauri の `primary_monitor()` で取得し、サイズ/位置を scale_factor で論理座標に正規化する。

> 変更理由: 旧仕様は「付箋を飛ばさない」優先でモニターごとに整列したが、ユーザーの使い方では
> 「同じタグが画面ごとにバラける」方が困る。**全部を1画面に集めて俯瞰できる**ことを優先する（ユーザー確定）。

> 補足（確認済み）: タグと色を結びつける仕組みはコード上に存在しない
> （色変更=`backgroundColor` を書くだけ、タグ操作=`tags` を付け外すだけ。両者は独立）。
> よって「タグのかたまりの中を色で分ける」2.1 の構造で、両方の情報をそのまま使う。

## 5 実装方針（状態管理の鉄則に沿う）

**ブランチ運用（確定）**: 整列本体は新機能で規模が中〜大のため、**専用ブランチで開発し `develop` へ PR**する
（リリース手順書 `docs/010_RELEASE.md` の「アプリに影響する大きい変更」に該当）。
前提タスク（第2章）が `develop` に入った後に着手する。

唯一の状態は Rust `AppState`。整列の位置計算は **Rust 側で行い**、各ウィンドウへ反映する。
フロントは state を持たず、ボタン/ショートカットで invoke するだけ。

| 手順 | 場所 | 内容 |
|------|------|------|
| 1 | Rust | `AppState` の全付箋から `tags`・`backgroundColor`・`window`(w,h) を取得 |
| 2 | Rust | 全付箋のタグ一覧を作る。各付箋は `tags[0]` のかたまりに振り分ける（タグなしは右端ブロック 4.3） |
| 3 | Rust | タグごとに（タグ順は 4.2）、中を色の固定順で列に分け、各付箋の新しい x,y を計算 |
| 4 | Rust | 各付箋ウィンドウの位置を反映し、frontmatter の `window` も更新 |
| 5 | フロント | ボタン/ショートカットで整列コマンドを invoke するだけ |

**参照する既存コード**
- 位置: frontmatter `window: { x, y, width, height }`（`src-tauri/src/logic.rs` の `re_window`）
- 色・タグ: `extract_meta_from_content`（`src-tauri/src/logic.rs`）が `(x,y,w,h,color,aot,tags,folded)` を返す
- 色定義: `app/hooks/useStickyNoteContextMenu.ts`（黄/赤/青。白/黒は前提タスクで追加）
- トレイUI: `src-tauri/src/tray.rs`
- 位置反映の注意: `fusen_show_at_position`（`src-tauri/src/lib.rs`）は表示/フォーカス用途で副作用が強い。
  整列にはそのまま使わず、**位置変更のみ・フォーカス変更なし**の専用経路を用意する。

### 5.1 座標系（重要・Codex 指摘）
- 既存の `app/api/window.ts` は OS の物理座標を scaleFactor で割り、frontmatter には**論理座標**で保存している。
- 一方 `fusen_show_at_position` は**物理座標**を受ける。座標系が混在しているので明示する。
- 方針: **計算・AppState・frontmatter は論理座標で統一**。OS へ移動する瞬間だけ物理座標へ変換する。
  monitor / workArea のサイズも同じ座標系（論理）に正規化してから計算する。

### 5.2 はみ出し・あふれの扱い（Codex 指摘）
- **横あふれ**: タグ数や色列が多く workArea 幅を超える場合、超えたタグブロックを次の段（下）へ折り返す。
- **巨大な付箋**（`width > workArea幅` / `height > workArea高さ`）: サイズは変えず、**左上だけ workArea 内に入れる**（はみ出しは許容）。

#### 5.2.1 横あふれ折り返しの詳細（部品⑥・確定 26-06-20）
実機確認（2026-06-20）で、付箋8枚が workArea 幅 2560 を超え x=3312 まで横一列に伸び、**画面外に飛んで見えない**不具合を確認。原因＝折り返し未実装。これを arrange.rs に実装する。

- **折り返し単位 = タグのかたまり（タグブロック）**（ユーザー確定）。タグの塊ごと次の段に送る。同じタグが途中で割れない。
- **判定**: 次に置くタグブロックの右端が `workArea.x + workArea.width` を超えるなら、そのタグブロックを**次の段（下）の先頭から**置く。
  - 次の段の開始 y = 「前の段で一番背が高かった付箋の下端」+ 段間マージン（例: ROW_GAP 流用 or 40px）。実装時に調整可。
  - 段の x は START_OFFSET_X に戻す。
- **1つのタグが単体で workArea 幅を超える場合**（巨大タグ）: そのタグは**1段に収まらなくても先頭から置き、はみ出しは許容**（5.2 の「巨大な付箋」と同じ思想＝サイズは変えない）。次のタグはその下の段から。
- arrange.rs の `calculate_arrange_by_tag_positions` に折り返しを入れる。**純粋関数のまま**（workArea 幅で改段するロジックを追加）。既存テスト7件を壊さず、折り返しの単体テストを追加する。

### 5.3 反映順序と途中失敗（Codex 指摘）
- 順序は「新配置を計算 → 各ウィンドウを移動 → **成功した分だけ** AppState と frontmatter を更新」。
- 途中で移動に失敗した付箋は、その付箋だけ元のまま据え置く（全体を巻き戻さない）。
- 位置だけの更新では frontmatter の **`updated` を変えない**（整列は内容変更ではないため。履歴・同期の意味を濁さない）。

### 5.4 一括移動のパフォーマンス・ちらつき（Codex 指摘）
- 逐次 `await set_position` は遅く、各ウィンドウを前面化するとちらつく。
- Rust 側で **フォーカスを奪わない一括移動**にする。必要なら小さなバッチで実行する。
- サイズ変更なし・位置変更のみ・フォーカス変更なしを前提にする。

### 5.5 実装の段分け（混在防止・1つずつ検証）

第1段は完了（`arrange.rs` の位置計算・純粋関数）。第2段を3つに分ける。

| 段 | 内容 | 検証 |
|----|------|------|
| 第1段 | 位置計算ロジック `arrange.rs`（純粋関数） | ✅ cargo test 7件 pass（feature/arrange-clean） |
| 2-a | 整列コマンド `fusen_arrange_by_tag`：付箋列挙→メタ取得→seqソート→arrange計算→位置反映→frontmatter更新 | ✅ 実装完了（部品①〜⑤・cargo build/test 7件 pass）。**実機確認待ち**＝仮トリガ Ctrl+Shift+L で押して動作確認（ユーザー帰宅後） |
| 2-b | トレイメニューに「タグで整列」追加 | 実機 |
| 2-c | undo（整列前スナップショット1段＋「整列前に戻す」） | 実機 |

### 5.6 2-a 実装指示（Codex 再開時にそのまま渡す）

**作るもの**: Rust コマンド `fusen_arrange_by_tag`（Rust 主導・状態の真実は AppState）。

**手順**:
1. 付箋ウィンドウを列挙: `app.webview_windows()` の `(label, window)` で `label != "main"` が付箋。
2. 各付箋について:
   - label から path を引く（既存の `get_window_label(path)` の逆引き、または AppState.notes と突き合わせ）。
   - 現在位置を取得: `window.outer_position()`（物理）を `window.scale_factor()` で割り**論理座標**にする
     （JS の `getWindowGeometry`＝`app/api/window.ts` と同じ換算）。※モニター判定には使わない。位置反映の参考用。
   - **モニター判定はしない**（4.4 確定＝全付箋をメインモニターに集約）。
3. **メインモニター1枚の作業領域(workArea)** を `primary_monitor()` から取得し scale_factor で論理座標に正規化 →
   全付箋を `ArrangeNote` に変換 →
   `arrange::calculate_arrange_by_tag_positions(notes, work_area)` で新座標（論理）を得る。
4. 各付箋を新座標へ移動: フォーカスを奪わない位置変更のみ（5.4）。論理→OS は内部で変換。
   `fusen_show_at_position` は副作用が強いので使わない（5.1/位置反映の注意）。
5. 移動に成功した付箋だけ frontmatter の `window` を更新（`updated` は変えない・5.3）。
   既存の window 正規表現フォーマット `window: { x, y, width, height }` を維持。

**制約**:
- トレイUI（2-b）・undo（2-c）は今回やらない。
- arrange.rs は完成済み・変更しない。`NoteMeta` の構造も変えない。
- StickyNote.tsx 等フロントの表示ロジックは触らない（編集高速化は別タスク）。

## 7 整列の取り消し（undo・確定）

ボタン1発で自由配置を上書きするので、**直前の1回だけ「整列前に戻す」**を入れる（1段undo）。

### 7.1 仕組み（整列前スナップショットを1段持つ）
- 整列する**直前に、全付箋の現在位置を1セット記録**する（スナップショット）。
- 記録先は Rust `AppState`（状態の真実は AppState の鉄則どおり）。**メモリのみ・ファイルに書かない**。
- 中身は `[(付箋のパス, 元の window=x/y/width/height), ...]` のリスト。
- スナップショットは**常に1枚だけ**。再度整列したら古いものを上書きする
  ＝戻せるのは「直前の整列前」だけ（複数段には**しない**。要望が出たら拡張）。
- アプリを閉じると消える（＝再起動後は戻せない）。これは許容。

### 7.2 3つの操作
| 操作 | やること |
|------|---------|
| 整列する | ①現在の全位置をスナップショットに保存 → ②計算して並べる |
| 戻す | スナップショットの位置を全付箋へ書き戻す → スナップショットを空にする |
| 戻せるか | スナップショットが空なら「整列前に戻す」を出さない／押せなくする |

- 「戻す」の位置書き戻しは、整列の位置反映（5.3）と**同じ経路を使い回す**（書き込む座標が違うだけ）。

### 7.3 スナップショット後に付箋が増減した場合
- **付箋のパスで照合**し、今あるものだけ戻す。
- 記録後に**消えた付箋**: 戻しようがないので無視。
- 記録後に**増えた付箋**: スナップショットに無いので動かさない（そのまま）。

> 補足: 7 以外の論点はすべて確定済み。5色以外の付箋（黒の右に「その他」列）は 3.3 を参照。
