# Phase 22: しまった付箋の選択復元 - Research

**Researched:** 2026-09-05
**Status:** Complete

## 現行構造

- しまう処理は `fusen_archive_note` が担当し、タグなしは `Archive/`、タグありは `tags/<tag>/` へMarkdownと関連画像を移す。
- 関連画像は各移動先の `assets/` に置かれ、本文の `assets/...` 参照は維持される。
- 設定画面の現行インポートはフォルダ直下の全Markdownを保存先へコピーするため、個別選択・元削除・同名拒否という今回の要件にはそのまま使えない。
- トレイ項目は `src-tauri/src/tray.rs` で作られ、メインウィンドウへイベントを送る既存パターンがある。
- `app/page.tsx` は検索・設定をメインウィンドウ内の排他的画面として開く。復元画面もこの経路へ合わせるのが変更範囲を抑えられる。
- 復元後の一覧再同期とウィンドウ表示には `fusen:notes_updated` と `fusen:open_imported_notes` の既存経路を再利用できる。

## 推奨アーキテクチャ

1. Rustに「しまった付箋一覧」と「選択付箋の一括復元」の2コマンドを追加する。
2. 一覧・復元の両方で、入力パスを信用せず現在のbase pathから許可対象を再解決する。
3. 復元は項目単位の結果を返し、1件の衝突や失敗で一括処理全体を中断しない。
4. 成功順序は、衝突確認 → 画像準備 → 復元先Markdown書込み → 元Markdown削除 → 未参照になった元画像の掃除、とする。
5. 画像名が保存先に存在する場合は上書きしない。固有名へコピーして復元本文のMarkdown参照を書き換える。
6. 元画像が同じしまったフォルダ内の別付箋からも参照される場合は削除しない。
7. UIはデータ取得・検索・選択・結果表示に限定し、ファイル操作の判断はRustへ集約する。

## 主なリスクと対策

| リスク | 対策 |
|---|---|
| `../` 等で任意ファイルを移動できる | UIから来た絶対パスをcanonicalizeし、`Archive/`直下または`tags/<tag>/`直下の `.md` のみ許可 |
| 同名付箋を上書きする | 復元先の存在確認をRustで必須化し、当該項目をconflictとして返す |
| 同名画像を上書きする | 一意な画像名を生成し、本文参照を書き換える |
| 途中失敗で元も先も壊れる | 元Markdownは復元先書込み完了まで削除しない。画像掃除は最後に行う |
| 共有画像を消す | 元フォルダの残存Markdown参照を確認して未参照画像だけ削除 |
| 復元後に表示されない | 成功パスだけ既存の再同期・ウィンドウ生成イベントへ渡す |

## テスト方針

- Rust単体テストを中心に、列挙範囲、パストラバーサル、同名拒否、部分成功、画像衝突、共有画像、途中失敗を一時ディレクトリで検証する。
- Reactテストで絞り込み、複数選択、ボタン件数、部分失敗結果、閉じる操作を検証する。
- E2Eでトレイ相当イベントから画面表示し、復元成功パスが即時表示イベントへ渡ることを検証する。
- 実機で実際のArchive・タグ・画像付き付箋を各1枚復元し、元削除とデスクトップ表示を確認する。
