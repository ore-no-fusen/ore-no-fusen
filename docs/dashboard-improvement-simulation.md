# 利用データから改善を選ぶシミュレーション

作成日: 2026-10-06。以下は架空の数値を使った判断練習であり、現在の会員の実測結果ではない。比率だけで原因は確定しない。

## 最初に確認する分母

- 全会員比 = 今週使った報告会員 / 全登録会員。普及規模を見る。
- 報告者内比 = 今週使った報告会員 / 今週の利用情報が届いた同意済み会員。報告者の中の利用状況を見る。全利用者の代表とは限らない。
- iPhone連携では、送信した人と受信した人を重複排除した人数が必要。送信人数と受信人数を足してはいけない。
- iPhoneを持ち、連携を使いたい人に対する利用率は現状不明。全会員比が低くても需要が低いとは限らない。
- 本番と検証は別々に判断する。開発者の検証操作を本番の利用傾向に混ぜない。
- 本番送信は前回成功から24時間後。今週の値は週の途中で増える。日付はUTC、GA4の本日アクティブとは集計元が違う。

## iPhone連携が2%だった場合

全登録200人、送信または受信した会員4人と仮定する。

| 観測 | 計算 | 最初の対応 | 次に確かめること |
|---|---|---|---|
| 利用情報の報告が20人だけ | 全会員比2%、報告者内比20% | 計測範囲と送信待ちを確認。機能の作り直しを決めない | 報告人数と版の分布。翌週以降も同じ条件で見る |
| 報告160人、試した人数は不明 | 全会員比2%、報告者内比2.5% | お便りで用途と設定手順を1回案内し、困った点を募る | 読まれたか・試されたか。周知後の人数変化 |
| 連携を試した40人、成功4人（追加情報を仮定） | 初回成功率10% | 周知を増やす前に設定・通信失敗を調べる | 設定のどの段階で止まるか、エラー種類 |
| 案内を見た50人、試した5人、成功4人（追加情報を仮定） | 試行率10%、成功率80% | 具体的な使い道を見せる。iPhoneの有無・必要性を少人数に聞く | 不要なのか、入口が見つからないのか |
| 初回成功20人、翌週も使用4人（追加情報を仮定） | 対象者の翌週利用率20% | 使い続けられない理由を聞く。速度・手間・用途を検討 | 失敗したのか、単発用途なのか |

周知によって利用が4人から12人になれば、分母200人固定なら2%から6%になる。ただし、登録者増・報告者の入れ替わり・週の途中・版更新で増えた可能性も確認する。「周知が原因」と断定しない。まず周知、次に導入時のつまずき、最後に日常利用の手間の順に仮説を絞る。

## 各データが多い・少ないとき

| 指標 | 多いときの対応 | 少ないときの対応 | 判断を助ける追加情報 |
|---|---|---|---|
| 新規登録 | 新規会員の初回利用・翌週利用を確認。登録増だけを成功としない | 流入と登録途中の離脱を分けて調べる | 流入元、登録完了率、初回成功 |
| 過去7日の通信人数 | 常駐での通信と実操作を分ける。頻用機能の操作を短くする | 通信不良・未報告・利用停止を切り分け、少人数に理由を聞く | 操作した日数、通信エラー、再訪 |
| 対象版の普及率 | その版の不具合・性能を優先確認 | 最近通信した会員に限って更新案内・更新失敗を調べる | 更新提示、更新試行、成功/失敗 |
| 付箋作成・編集 | 頻用操作の速度、保存安定性、ショートカットを優先 | 作成前につまずくのか、既存付箋を見る用途なのか確認 | 初回作成成功、編集失敗、用途 |
| 検索 | 検索を開く人数だけで評価せず、見つかる速さを改善 | 付箋が少なく不要か、検索入口を知らないか確認 | 付箋枚数の区分、検索後に開いたか、所要時間 |
| タグ・アウトライン | 整理機能の操作回数・手間を減らす | 整理が必要な会員へ使い方を案内して反応を見る | 付箋枚数の区分、入口の認知、実例への反応 |
| アラーム | 設定よりも通知の到達・解除の分かりやすさを確認 | 必要性を聞く。低頻度でも価値が高ければ維持する | 通知到達、見逃し、設定失敗 |
| 複製・アーカイブ | 繰り返し作業や整理の手間を減らす | 毎週使う必要はないため、頻度だけで廃止しない | 操作を完了できたか、必要な場面 |
| 画像添付 | 保存・表示・PC/iPhone往復の安定性を優先 | 入口や対応形式を案内。失敗があれば先に直す | 添付試行、成功/失敗、サイズ区分 |
| 累計起動時間 | 常駐時間を含むので、操作頻度や負荷と併せて見る | 新規会員、未集計、短時間用途を分ける | 登録からの期間、操作日数、週別時間 |
| 計測報告人数 | 代表性と集計時期を確認したうえで比較 | 改善判断を保留し、送信周期・同意・計測対応版を確認 | 同意率、送信失敗、版別の計測対応 |

## 足りない情報と追加順

1. **利用の過程**: 周知表示 → 入口クリック → 設定開始 → 設定完了 → 初回送受信成功、失敗段階と粗いエラー分類。本文・画像・検索語は不要。現状のPCのiphone_sendは送信コマンド完了後、iphone_receiveは受信付箋処理後に記録される。これだけでは入口クリックやiPhone上で実際に読めたかは分からない。
2. **継続利用**: 登録週・初回利用週ごとの翌週利用。累計起動時間では離脱や再訪を判定できない。履歴を持つ集計が必要であり、現在の週次会員データだけでは直接算出できない。
3. **利用目的と対象者**: iPhoneの有無、連携の必要性、未使用理由を任意の短い質問で確認する。全会員への自動収集を前提にしない。
4. **周知の効果**: 届いた人数、見た人数、試した人数、成功した人数。送信しただけでは周知されたとは言えない。

追加計測は提案段階。今回の画面改善では新しい利用情報を収集・送信しない。計測の追加は既存の同意・仕様・プライバシーの範囲を確認して別途実装する。

## 実行するなら

最初はiPhone連携だけを対象に、同意済みの未使用者へ「外出先でPCの付箋を見る」等の用途と最短手順を1回案内する。案内期間と比較期間を記録し、完了した週を2〜4週見る（これは今回の実験案であり、統計的な保証ではない）。人数が少ない場合は割合の上下より実人数と任意の返信を優先する。失敗の声が集まれば修正、入口が分からない声なら導線改善、不要という声なら他の頻用機能へ優先度を移す。
