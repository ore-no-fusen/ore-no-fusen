# テスト・検査の実施順と分類

2026-10-27。45件は個別のテストケース数ではなく、検査・ビルド・実機確認の実行単位です。個別237ファイルは [機能別索引](TEST_FILE_INDEX.md) に掲載します。

## 読み方

**大分類は主な工程に近い掲載順、その中は軽い検査から後段の確認へ並べています。番号を先頭から最後まで一度ずつ直列実行する意味ではありません。** 中分類は列、実際の前後関係は「順序・前提」と次の工程表で確認します。実機・CI集約は複数回登場し、試作は独立した補助分類です。

Astraと現行hook・workflow・運用正本を照合しました。今回は掲載順と説明の整理のみで、CI設定・実行コマンド・PC/CIの対象条件は変更していません。正式リリースの正本は [010_RELEASE.md](010_RELEASE.md)、通常統合は [CI_MERGE_POLICY.md](CI_MERGE_POLICY.md) です。

表2：実装で確認した順序（並べ替え済みの実装と誤解しないための対照）

|経路|現行の実行順・依存|今回の掲載順との関係|
|---|---|---|
|PC hook|差分判定 → 型とVitestを並列 → 対象時E2E|軽量検査を先に置く。ただしLintは独立自動実行されない|
|Test内frontend|release engine → UI → export境界/ガイドbuild → ガイドE2E → 運用回帰 → Discord → Vitest → 型 → Tauri画面build|型・単体を早期に見る掲載順と現行CI順は異なる。現行順の変更は未実装|
|Testの各job|scope後に対象jobを並列 → 必要時MSIX → gate|大分類のT02〜T05を無条件に直列化しない。全適用対象を確認する|
|MSIX CI内|証明書 → Web/API build → Tauri exe（画面build含む）→ 梱包/署名 → 署名検証 → 導入/起動|版番号/構文/梱包回帰は同じjobの前段ステップとは限らない。単独起動時だけJS/Rustテストも追加|

|Vercel|PR/統合後に自分でbuild・配信する独立経路|T06-01の成果物を受け取って、その後に配信する意味ではない|

**自動化コードの回帰試験は、実際のリリース処理を実行する工程とは別です。** 例えばT01-05/06はリリース制御・画面を試すテストであり、Store提出を行いません。T01-08/09も実際のMSIX結果記録・成果物削除の工程とは別です。

## PCの「自動」の前提

新しいworktreeでは、node_modulesを共有しただけではHuskyの起動用ファイルが作られず、Git設定があってもhookが実行されない場合があります。**作業場所ごとに `npm run prepare` を実行し、`.husky/_/pre-commit` の存在を確認**します。`HUSKY=0`等の無効化がないことも確認します。文書CI見直し時には未準備を検出して準備し直し、全975件と型検査の成功を確認しました。

また、hookは作業フォルダーを検査するため、未ステージの変更を混ぜたまま「コミット対象を検査した」とは保証できません。PC結果をGitHubで再利用する前に、候補内容・base・依存・条件・結果を一致させる仕組みが必要です。
