# テスト・検査の一覧

2026-10-27。**T番号はテスト・静的検査・動作確認だけ**に付けます。大項目は「何をテストするか」、中項目は「その中のどの機能・役割か」、個別項目は「何が正しければ合格か」です。

大項目は設計書→画面→内部処理→連携・全体動作→性能→配布・更新の順。中項目は実際の使用・処理の流れ、同じ機能内は正常動作→条件違い・境界→失敗時・復旧の順で整理します。既存の一括テストを架空に分割したり、存在しない検査を追加したりしません。承認された一覧の順番を維持しています。

PC/GitHub、自動/手動、実施時期・条件は分類に混ぜず別列です。**33項目は実行単位であり個別テストケース数ではありません。以前の45項目は検査33項目と準備・実行・結果確認12項目を含んでいました。** 要求整理・設計書作成・実装など15の作成作業もT一覧から除外しました。検査・CI・hookの実行内容や条件は変更していません。

個別237ファイルは[機能別索引](TEST_FILE_INDEX.md)、場面別の実施対象は[作業パターン×検査マトリクス](TEST_USE_CASE_MATRIX.md)を参照します。正式リリースは[010_RELEASE.md](010_RELEASE.md)、通常統合は[CI_MERGE_POLICY.md](CI_MERGE_POLICY.md)が正本です。

### 工程と実行順

要求整理→設計→画面・内部処理の実装→対象テスト→配布物作成→導入・実機確認→申請・公開後確認という開発の流れを維持します。作成作業をテストと数えません。T分類の掲載順はCIコマンドの厳密な直列実行順ではありません。

- PC通常コミット直前：文書判定→型検査T02-02とVitest T02-01を並列→対象時に全体E2E T02-04。版番号限定モードだけT06-01。
- PR/統合後CI：判定器の回帰T03-05→実際の対象判定→対象jobを並列→必要時MSIX→CI結果の集約。T03-05の判定器を試すテストと、実際に判定する処理は別です。
- frontendの現行順：リリース制御→管理画面→公開原稿境界/マニュアルbuild→ガイドE2E→運用回帰→Discord→Vitest→型→Tauri画面build。分類順への実装変更はしていません。
- MSIXの現行順：証明書準備→Web/API build→Tauri exe（画面build含む）→梱包/署名→署名検証T06-05→導入・起動T06-06。単独手動起動時のみ追加検査がある条件も従来どおりです。
- マージ前：最新head/base/merge候補と、全適用CI・別workflow・必要Vercelの成功を確認。CI gate成功だけで統合しません。
- iPhone実機T04-04はdevelop統合後のCI・Preview反映確認後。正式なPC実機T04-03、Store提出物T06-07、Store更新T06-08は各所定工程で実施。

T03-08〜11はリリース・復旧・結果判定・保全のロジックを試すもので、Store申請や実成果物の削除を行う工程ではありません。CI用exeと正式提出exeは別です。正式には実機合格した同じexeをStore用に再利用し、確認待ちだけを理由に再buildしません。

## PC検査の準備と削減候補

新規worktreeではnpm run prepareと.husky/_/pre-commitを確認し、hookを無効化しません。PC結果再利用には候補内容・base・依存・コマンド/設定・環境・成功結果の一致証跡が必要です。通常hook成功だけでCIを省略しません。

文書コンテンツのみの変更はアプリ検査を省略し、scope・文書差分検査・必要な文書build/リンク検査・gateを行います。設定・依存・実行コード・混在・未知の変更は通常判定を維持します。

- Tauri画面build：通常MSIX時にfrontendとbeforeBuildで2回。集約は後続候補で未修正。
- T02-01/02/05：PCとCIの正確な入力一致を確認して再利用する候補。
- 運用・連携等の回帰：共通依存を含む変更範囲を確認して選択実行する候補。
- 公開マニュアルbuildと外部Vercel：対象/環境を照合してから整理する候補。
