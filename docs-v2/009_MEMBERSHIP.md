# 009 会員番号と機能利用分析

承認日: 26-09-04。実装中。配信前に本書の実機確認を完了する。

本書は、会員番号、利用情報の収集、お便りの配信、開発者ダッシュボードを定義する。

**ダッシュボードの目的・見方・使用／未使用の判断は「5 開発者ダッシュボード」を参照する。** 利用情報を送る仕組みは「3 機能利用分析」、お便りを配信する仕組みは「4 開発者ホットライン」に記載する。

## 1 識別と保存

固定IDをRustで一度だけ生成し、一般番号はサーバーが10000から採番する。有料番号は別枠で将来1から採番し、両方を同じ固定IDに対応付ける。今回は決済接続を行わず、未接続を未購入とは扱わない。番号は認証秘密ではない。再インストール・別PCの同一人物性を番号だけで証明しない。

会員台帳の正本はFirestore、PC側の唯一の実行時状態はRust AppStateとする。資格情報をWindowsで保護し、画面取得・全窓イベント・ログ・分析には秘密を含めない。本番と開発の資格情報、API、採番を分離する。DB未設定時のメモリ代替は禁止。

同一実行ファイルを使う開発署名MSIXとStore用MSIXは実行時のパッケージ名ONFStudios.FUSEN.Dev/ONFStudios.FUSENで環境を分離する。MSIXであるかどうかだけでは判定しない。

通常の同一配布環境でのバージョン更新ではID・資格情報を移行/保持し、番号を再発行しない。保存パスにアプリバージョンを含めない。アンインストール時のデータ保持は未検証で、残存した資格情報を復号できれば同じ番号を取得する。資格情報も消えた場合は新規登録となる。Storeアンインストール/再インストール、Windowsのアプリリセットを別々の実機確認項目とする。試験はユーザーの本番データを使わず隔離環境で行う。会員番号だけでは復元認証を成立させない。

## 3 機能利用分析

### 3.1 同意と個人情報の扱い

初回の同意画面は640×520論理ピクセルで表示する。設定読込み中は通常画面への縮小を行わず、同意画面表示中は他のリサイズポリシーで上書きしない。小さいウィンドウでは画面内のスクロールで説明・詳細・両方の選択ボタンへ到達できるようにする。

会員番号の発行と分析同意を分離する。「改善のための利用情報の送信」という一つの設定で、すべての利用情報の収集・送信を判定する。同意を断っても全機能が利用できる。会員番号はGA4へ送らず、Firestoreに保存するランダムな分析IDをGA4 User-IDとして使用する。

**表 3.1-1　同意の選択と変更**

| タイミング | 動作 |
|---|---|

| 「協力する」を選ぶ | 利用情報の収集・送信を有効にする。 |
| 「送信しない」を選ぶ | 利用情報の収集・送信を停止する。未送信の集計と累計起動時間を削除する。 |

### 3.3 保存する情報

週はUTCの月曜日から日曜日までとし、ISO週番号 `YYYY-Www` で識別する。

**表 3.3-1　利用分析で扱う情報**

| 項目 | 内容 |
|---|---|
| 集計情報 | 固定機能名、週間使用回数、使用日数、最終使用日、アプリ版、計測版。 |
| 最新週の互換スナップショット | 会員台帳に今週使った機能の一覧と累計起動時間を保持する。旧ダッシュボード/APIとの互換用。 |
| 週別利用履歴 | 別の`usage_history`文書に週・計測スキーマ・アプリ版・対応機能・観測開始日時・日別観測時刻・機能別初回/最終実利用時刻・回数を保存する。会員と結ぶ内部キーは既存のランダム分析ID。インストールごとのランダム報告者IDで同一端末の再送を上書きし、別端末の履歴は保持する。 |
| 初回実利用 | 利用分析に同意後、計測対応版で成功した機能操作を最初に記録した時刻。計測開始前の実際の初回利用日時を意味しない。日付境界と期間判定はUTCに統一する。 |
| 保存・送信しない内容 | 付箋本文、検索語、タグ名、添付内容、画像、パス、生の操作列。 |
| 同意撤回時 | PC内の未送信集計・観測・初回/最終実利用時刻とFirestore側の最新週利用情報・週別履歴を削除する。以後は同意済みになるまで機能利用を収集しない。 |

### 3.4 集計と送信のタイミング

成功した操作は画面上で同一ターン内に集計し、操作完了後にRustへ非同期通知する。Rustは保存済み設定から同意を再確認し、受信バッチと一意IDを暗号化ローカルファイルへ原子的に保存する。IPC失敗時は画面側で同じバッチを再試行し、RustはIDで重複を無視する。通常操作からGA4・Vercelへはアクセスせず、付箋の操作を待たせない。文字入力はキー単位で数えず、保存に成功した編集を1回とする。他の機能も成功時だけ数える。起動60秒後と常駐中の約3時間ごとの確認で利用情報を同期する。同意、対象週、今週使った機能の一覧が前回成功時から変わった場合に送信する。変更がなければ再送せず、起動時間だけの増加も追加送信の理由にしない。既存データに前回送信した機能一覧がない場合は、保持している利用記録を再送する。送信成功時だけ週・機能一覧を保存し、失敗時は次の確認で再試行する。heartbeatは引き続き本番で前回成功から24時間後、GA4送信は翌週の起動から60秒経過後とする。同意変更時は次のheartbeatを待たずに同期し、同意撤回をFirestoreへ反映する。同意撤回は画面の保留バッチを破棄し、Rust側の保存済み利用記録も削除する。

計測スキーマ3では、同意済みのメイン画面が起動時・5分ごとに観測日を記録し、成功した機能操作にはUTC時刻を付ける。利用履歴は約3時間ごとに最新スナップショットとまとめて送る。Firestore保存は`analyticsSubject + 週 + インストール報告者ID`で分け、同一端末の再送を同じ文書へ統合する。機能ごとの日別利用回数は同一端末では最大値、利用日・機能一覧は和集合とするため、再送で利用済み機能が消えず二重加算もしない。別端末は別報告者として保持し、利用率では会員単位の和集合にする。会員台帳にある最新週フィールドは引き続き更新する。同意を未選択へ戻した場合は、機能情報を載せず`usageConsent: null`として状態を区別し、履歴を削除する。明示的な拒否は`false`のまま保持し、同意へ変更しない。

計測未同意、旧版、未起動、送信失敗を利用ゼロと扱わない。週次完了イベントを受信した分析IDだけを分母にする。GA4では個別分析IDの回数と、全体の利用者率・中央値・分布を確認する。会員番号との照合が必要な場合だけ、管理者専用APIをBearer認証して番号索引から1件を直接検索する。APIは一般番号、匿名分析ID、登録日時、有料番号だけを返し、会員ID・認証秘密・利用履歴は返さない。ユーザー向け利用状況画面は追加しない。

## 4 開発者ホットライン

PCのメイン画面は起動60秒後と常駐中に、分析同意の有無にかかわらず会員認証付きでお便りを確認する。本番では前回の確認要求から約3時間ごと、開発環境では約5分ごとに確認する。5分周期のPC内タイマーは送信要否を判定するだけで、毎回APIへ接続しない。移行後の初回確認は旧版の24時間制限を引き継がず、次回以降の再起動では保存した確認時刻を引き継ぐ。スリープ中・終了中は確認しない。失敗時は最後の成功時刻と受信済みのお便りを保ち、本番は約15分後、開発は約5分後に再試行する。同時要求を抑止し、保存失敗時は受信済みとして扱わない。「開発者とのやりとり」には最終成功日時と確認失敗を表示する。

会員台帳を更新するheartbeatは、本番で前回成功から24時間後に送る。ただし新版へ更新後の最初の起動では24時間未満でも新版を報告する。それ以外のお便り確認は読み取り専用のannouncements APIを使い、会員台帳へ書き込まない。heartbeatが必要なときはお便りの取得も同じ要求で行い、追加要求を避ける。保存済みのお便りでは通知を再表示しない。APIは会員台帳の互換用の`lastSeenAt`をUTC日付、`lastSeenTimestamp`をUTC通信時刻で更新し、報告されたアプリ版を同じ会員レコードに保存する。版番号を送らない旧版からの通信では版を未報告に戻す。

開発者はローカルダッシュボードからタイトルとMarkdown本文を投稿する。宛先は全会員、古参会員（会員番号10000〜10049）、新規会員（10100以降）、今週の機能利用あり、今週の計測対応済み記録に機能名なし（利用分析に同意済み）、または登録済みの会員番号1件を選べる。投稿は30日間有効とする。未登録番号・不明な宛先は保存しない。ダッシュボードでは過去に送信したお便りを期限切れも含めて新しい順に読み出し、日時・宛先・タイトル・本文・配信状態を確認できる。配信中のお便りは確認操作を経て配信停止できる。停止後も履歴と既にPCへ届いたお便りは残し、次回以降の配信対象から外す。個別宛てと会員番号で判定できる区分はAPIでも対象外会員へ本文を返さない。機能利用による区分はPC内にしか判定材料がないため、APIから配信された後にRustで対象判定する。機能利用区分には機密の本文を使わない。

受信したお便りはPC内の保護された会員データに保存し、設定画面の「開発者とのやりとり」に表示する。新着時は通知の小窓だけを出し、通知ボタンを押したときに会話画面へ移動する。通知のボタンまたは閉じるボタンで小窓を閉じてもアプリは終了しない。会話画面には受信件数を明示する。返信先IDが一致するユーザーの返信は、お便りカード内に古い順でまとめる。スレッドは最後の返信時刻で並べ、最近のものを下へ置く。返信先が分からない通常の発言と開発者の発言は独立表示し、推測でスレッドに結び付けない。開いた直後は最新の位置を表示する。お便りカードの直下で返信を入力でき、送信内容にはお便りのタイトルとIDを付けて会話として送信する。会話APIの取得に失敗しても、保存済みのお便り本文は表示する。付箋には追加しない。

サーバーは配信中・期限内のお便り一覧を環境ごとに最大5分間、同じ実行インスタンス内で共有し、会員ごとの履歴全件読み取りを抑える。投稿・配信停止の反映には最大5分程度の一覧更新待ちが加わる。期限と宛先は応答時にも判定し、必ず会員認証後に本文を絞る。認証情報・会員台帳・宛先別API応答はキャッシュしない。失敗した一覧取得はキャッシュしない。別インスタンスや再起動時は再取得するため、無料枠内の保証や履歴増加に対する恒久的な読み取り削減ではない。既存のお便りと旧版heartbeatにも対応する。

今週の機能別宛先は対象機能を選ぶ。利用ありは今週の記録がある会員、記録なしは計測スキーマ3以降で当該機能への対応が確認できる週記録があり、機能記録がない同意済み会員を対象とする。週記録がない旧版・未起動・送信失敗等の会員は利用なしとみなさない。iPhone連携の記録なしも、今週のスキーマ3週記録で送受信の両方に対応し、どちらの記録もない会員に限る。機能の利用判定はPC内で行い、同意していない会員を対象にしない。

## 5 開発者ダッシュボード

新着お便り・返信の通知小窓は共通の表示枠を使う。長い件名・複数件の通知でも読むボタンを画面内に残し、件名は省略せずスクロールで読めるようにする。

### 5.1 目的

**ユーザーがどの機能を使っているかを把握し、周知や機能改善の判断に使う。** 会員が増えても、全体の傾向と確認が必要な会員をすぐに見つけられる画面にする。

本番用と検証用は同じ表示ルールを使い、データを混ぜない。画面上部に対象環境と集計日時を表示する。

### 5.2 画面の構成

**表 5.2-1　四つの表示と確認できること**

| 表示 | 確認できること |
|---|---|
| 概要 | 総会員数、新規登録、最近の通信状況、アプリ版別人数、更新状況、会員数の推移。 |
| 会員一覧 | 会員番号、アプリ版、最終通信日、累計起動時間、利用情報の状態。検索・絞り込み・並べ替えを行い、25件ずつ表示する。 |
| 機能利用 | 今週の利用情報が届いた人数、対象機能ごとの利用人数と割合、GA4のイベント受信件数。 |
| 継続・離脱候補の比較 | 直近168時間の実利用で分けたアクティブ/離脱候補と、計測開始後の初回実利用から168時間における機能利用率、差、案内強化候補、匿名JSON。 |
| お便り | 宛先を指定した投稿、送信済み履歴、配信状態、配信停止。配信条件は4章に定義する。 |

概要の版別人数、機能利用の状態別人数を押すと、該当する会員に絞った会員一覧へ移動する。

比較画面の「アクティブ」は直近168時間に同意済み計測対応機能の実利用があった会員。「離脱候補」は計測開始後に実利用があり、直近168時間の日別観測がそろい、同期間の実利用がない会員とする。通信日時・登録日時だけでは実利用と判定しない。新規（初回実利用から168時間未満）、旧版・未計測、同意拒否/不明、観測不足は別分類にする。

初回利用比較は初回実利用から168時間が経過し、その期間の全日で観測があり、全12機能が計測対応版で観測された会員だけを分母とする。機能利用率差はアクティブ群の率から離脱候補群の率を引いたパーセントポイントで、正の差が大きい順を案内強化候補にする。各群20人未満は参考値と明記する。初回7日間の過去情報が存在しない既存会員は初回比較に補完せず、計測開始後に新しい実利用が得られるまで別表示とする。

分析JSONは会員IDと秘密情報を含めず、ローカルにだけ保存するHMAC鍵から作る安定仮名ID、初回/最終実利用時刻、同意・計測状態、日/週別機能利用、観測範囲と欠測理由を含める。HMAC鍵は出力JSONへ含めない。GA4の週・機能別全体集計は会員別実利用履歴に結合しない。

### 5.3 利用を確認する対象機能

対象は次の12機能である。**機能名はあらかじめ決まっている。機能利用の記録がない場合は「未記録・実利用不明」とし、未使用と断定しない。**

**表 5.3-1　対象機能**

| No. | 機能 |
|---|---|
| 1 | 付箋の作成 |
| 2 | 付箋の編集 |
| 3 | タグの追加 |
| 4 | アラームの設定 |
| 5 | iPhoneへ送信 |
| 6 | iPhoneから受信 |
| 7 | 検索画面を開く |
| 8 | 付箋の複製 |

| 11 | 画像の添付 |
| 12 | クイックランチャーへしまう |

クイックランチャー格納は`launcher_store`としてRustの格納完了経路で記録する。タグ一括格納は成功した付箋1枚につき1回。保存失敗、取り出し、格納済みへの再要求は数えない。記録は分析同意時だけ集計し、受信した各バッチとその重複排除IDを暗号化されたPC内会員ファイルへ原子的に保存する。利用情報に`usageSchema: 2`を付け、旧版（未指定または1）は格納利用を判定しない。格納行の報告者内比は計測対応版の今週報告者だけを分母とし、対応報告が0件なら「不明」。終了週の回数・使用日数は既存GA4週次送信を使う。

### 5.4 データの意味と利用記録の判定

ここでいう「利用情報」は、アプリが自動で送る利用記録である。ユーザーが報告文を書く操作ではない。

利用情報には、その週に記録された対象機能の一覧が入る。受信した一覧が空でも、計測・キュー・PC保存・送信の各段階で欠落していない保証はないため、実利用なしとは判定しない。

**表 5.4-1　会員ごとの判定ルール**

| データの状態 | 各機能の表示 |
|---|---|
| 今週の利用情報にその機能の記録がある | 利用記録あり |
| 今週の通信は届いたが、その機能の記録がない | 未記録。実利用なしとは断定できない。 |
| 今週の利用情報が届いていない、送信がオフ、または判定に必要な情報が不足 | 不明。利用記録なしの人数へも加えない。 |

**「機能利用の記録がある」「通信はあるが機能利用の記録がない」「今週の利用情報がない」を区別する。** 利用記録がない状態を未使用と表現しない。

| 付箋の作成 | 利用記録あり |

### 5.5 利用情報の到着状況

最初に、送信の設定と情報の到着を別々に表示する。

**表 5.5-1　送信設定と到着人数**

| 表示 | 意味 |
|---|---|
| 送信を許可（確認済み） | 最後に届いた設定が許可。今週の情報が届いていない人も含む。 |
| 送信を停止（確認済み） | 最後に届いた設定が停止。 |
| 送信の設定が未確認 | 設定が届いていない、または有効な許可・停止の値がない。どちらにも数えない。 |
| 今週の情報が届いた | 今週の利用情報が届いた人数。許可人数の内訳として表示する。 |

許可・停止・未確認の合計は全会員数と一致する。到着人数はこれらへ加算しない。旧版が送った設定は旧来の会員別分析の選択であり、初回に協力を選んだ人数とは限らない。更新後の共通設定が届くまで将来の到着人数は確定しない。

機能利用の画面では、全会員を次の五つに分けて人数を表示する。各会員は一つの状態だけに属し、合計は全会員数と一致する。

**表 5.5-2　状態別人数の意味**

| 表示 | 意味 |
|---|---|
| 機能名の記録あり | 今週の情報が届き、少なくとも一つの機能名がある。 |
| 機能名の記録なし（実利用は不明） | 今週の通信は届いたが機能名はない。未使用か記録欠落かを判定できない。 |
| 今週分はまだ届いていない | 以前の情報はあるが、今週分がない。今週の各機能は不明。 |
| 利用情報の送信がオフ | 最後に届いた情報で送信がオフ。各機能は不明。 |
| 情報がなく、まだ分からない | 利用情報がない、または判定に必要な情報が不足。各機能は不明。 |

送信がオフかどうかは、最後に届いた設定で判定する。情報がない理由を、未起動・旧版・通信失敗などと推測して表示しない。

### 5.6 機能別人数と割合

同じ会員が何回使っても、機能ごとの利用人数は1人として数える。対象期間はUTCの月曜日から日曜日までの今週である。

**表 5.6-1　集計値の読み方**

| 項目 | 計算・表示ルール |
|---|---|
| 今週の情報が届いた人数 | 今週の利用情報が届いた、利用分析に同意済みの会員数。 |
| 機能ごとの記録人数 | 今週の情報が届いた会員のうち、その機能の利用記録が届いた人数。 |
| 機能記録なし | 機能名が保存されていない状態。未使用か、計測・キュー・PC保存・送信中に記録が欠けたかは区別できない。 |
| 全会員比 | 機能記録人数 ÷ 全会員数。情報が届いていない会員も分母に含むため、全会員の実際の使用率を確定する値ではない。 |
| 今週の情報が届いた会員内の記録率 | 機能記録人数 ÷ 今週の情報が届いた人数。画面の報告者内記録率はこの値を指す。 |
| 情報が届いた会員がいて、機能記録が0人 | 記録人数は0人、記録率は0%。実利用がなかった証明ではなく、未使用と断定しない。 |
| 今週の情報が届いた会員が0人 | 今週の機能利用は不明。人数・割合は「不明」または「—」とし、未使用0人・使用率0%と表示しない。 |

たとえば全会員100人のうち、今週の情報が届いた人が10人、iPhone送信の利用記録が2人なら、記録あり2人・機能記録なし8人・今週の情報なし90人となる。全会員比は2%、報告者内の記録率は20%である。機能記録なしの8人を未使用とは数えない。

周知や機能改善の判断では、割合だけでなく、対象期間・全会員数・情報が届いた人数を一緒に見る。上の例の2%だけを見て「98人が未使用」と判断しない。

## 6 合格条件

2個体の異なる操作が別の分析IDに対応し、全体集計とも一致することを確認する。通常操作でネットワーク通信とディスク書込みが発生しないこと、操作経路の追加処理が10ミリ秒未満であること、集計失敗時も付箋操作が成功することを計測する。同時登録・複数窓・更新・同意撤回・保存失敗・無権限取得も検証する。本番DBの番号保持とGA4週次受信を実際に確認するまでリリースしない。
